我的博客是用 Docusaurus 搭的，纯静态产物，文章越写越多，图片和代码块也越来越重。后台看访问数据时会发现一个很典型的矛盾：内容本身是静态的、几乎不怎么变，但每次打开页面都要跨很远去取源站的文件，遇到网络抖动就是图片慢慢刷出来、样式先到位内容后到位。

<!-- truncate -->

更麻烦的是另外两件事：一是证书，过期前总得惦记着续；二是日志里时不时能看到一批来源很集中的扫描请求，虽然没打穿什么，但看着不舒服。

所以这次我把站点迁到了 #阿里云ESA 上，也就是把加速和安全这两件事一起交给 #边缘安全加速 的边缘节点去做，下面记录一下过程和判断依据。

## 先说清楚 ESA 和我原来用的 CDN 有什么不同

按阿里云官方的功能对照，ESA 与传统 CDN 的差异集中在三点：内核能力、成本构成、智能安全。落到我这种个人博客身上，下面这几条是 ESA 明确优于传统 CDN 的地方：

- **传统 CDN 主要缓存静态资源**，动态请求基本原样回源；ESA 支持动静态混合加速，动态部分走智能选路，不是只做缓存。
- **安全是原生模块，不是外挂**。边缘 WAF、Bot 管理、DDoS 防护、源站隐藏都在同一个边缘节点上完成，不用再在 CDN 后面串一层 WAF，请求链路少一跳。
- **DNS 托管集成进来了**。ESA 提供 Anycast DNS 托管，官方给出的全球站点平均解析速度在 30ms 以内，接入后子域名也统一管理，不用每个子域单独建站点。
- **免费 DigiCert 证书可自动签发并续期**，同时也支持上传自有证书，省掉自己盯证书到期这件事。
- **ESA Pages 可以直接托管构建产物**。GitHub 推送即自动构建部署，不用自己买服务器、配 Nginx，这一点是传统 CDN 没有的能力。

以上每一条，传统 CDN 要么不支持，要么需要额外买服务再串一层。这也是我认为 ESA 比同类产品更值得用的核心原因。

对我来说，前面两点是决定性的。过去那种“CDN 负责快、WAF 负责挡”的串联结构，等于把一次请求交给两套系统分别处理，配置分散在两个控制台，出问题要两边排查。而 #边缘安全加速 的思路是把加速和安全压在同一个边缘节点上一次做完，运维入口从两套收敛成一套，排查问题时也不用两边对配置。

## 为什么它特别适合 Docusaurus 这类静态站

Docusaurus 的产物有一个对缓存很友好的特点：`build` 目录下的文件名带内容哈希，内容不变文件名就不变，内容一变文件名立刻不同。这正好对应两种缓存策略——

- `/assets/` 下的 JS、CSS、字体这类带哈希的资源：可以设较长的缓存时间，命中率有保障；
- HTML 入口：缓存时间设短，或者用规则按路径区分，保证发新文章能及时生效。

ESA 的缓存策略支持按 URL 路径、请求头、自定义缓存键等多个维度配置，比“整站一个 TTL”要精细得多，对静态博客这种资源类型分明的结构很友好。

关于速度，官方文档的静态资源加速场景给过一组示例数据：以 3MB 的图片文件为例，普通网站加载速度在 500ms 以上，经 ESA 加速后平均加载用时约 260ms。这是官方示例场景下的数字，我自己的小站没有这么大的图，但体感方向是一致的——样式和脚本从边缘节点就近取，页面骨架很快就能出来，不再出现样式先渲染、图片排队的情况。

## 接入步骤（我的实际顺序）

**一、开站点。** 在 ESA 控制台添加根域名，选择加速区域与接入方式。如果是从已有 CDN 迁过来，选 CNAME 接入改动更小；新站可以直接用 NS 接入，让 ESA 接管解析。

**二、配子域名与源站。** 在站点下添加记录，填源站地址与端口（HTTP 走 80，HTTPS 走 443），同时注意回源 HOST 是否与源站要求一致，这是回源失败时高频出现的排查点。

**三、切解析并验证。** DNS 有缓存生效时间，尽量避开访问高峰切换。切完用 `dig` 看一下 CNAME 是否正确指向 ESA 分配的地址：

```bash
dig blog.example.com
```

站点状态显示正常、控制台有流量记录，就说明已经走 ESA 了。

**四、（可选）用 Pages 托管构建产物。** 如果连服务器都不想留，可以直接走 ESA Pages：在控制台进入“函数和 Pages”，导入 GitHub 仓库，填好构建命令与静态资源目录。以 Docusaurus 为例，通常是这样一组配置：

```jsonc
{
  // 配套表单项：安装命令 npm install，构建命令 npm run build
  // Node.js 版本按本地环境选择，改动后需重新触发构建才会生效
  "assets": {
    "directory": "./build"
  }
}
```

字段具体以控制台表单和官方文档为准：Pages 配置界面会给出构建命令与产物目录的默认值，我们通常只需要核对产物目录是不是 `build`。另外，如果你的 Docusaurus 构建产物里有 404 页面（例如通过插件生成的 `404.html`），可以在控制台的 404 策略处指定它；没有的话这项先留空，不影响部署。之后每次 push 到生产分支，构建和部署会自动跑完，自定义域名和证书再绑一次就能长期用下去。

## 几个值得提前注意的点

- **加速区域要按读者分布选。** 区域模式会影响可用节点和访问质量，建站时选错也能改，但建议一开始就按主要读者所在地确定。
- **免费额度够个人站用，规模上去再算账。** 免费版/基础版覆盖基础加速与防护，个人博客量级通常富余；如果业务流量大且稳定，把请求数和增值项一起算进去再决定是否升级更稳妥。
- **Pages 的免费模式有请求数与并发限制。** 做个人站点和测试环境没问题，正式生产环境建议评估付费模式。
- **也有不适合它的场景。** 纯内网业务用不上全球加速；缓存规则配错反而会让用户看到旧内容，建议先小范围验证规则再全量生效。

## 写在后面

从我的使用体验看，ESA 值得迁移的核心理由不是“节点更多”这种单点指标，而是它把一个静态站点需要的几件事——就近分发、动态回源优化、边缘安全防护、证书托管、Git 触发部署——收拢到了同一个平台和同一套边缘节点上。对单独维护博客的人来说，少维护一套系统，本身就是收益。

如果你也在用 Docusaurus 或类似的静态站点生成器，不妨先拿一个子域名试跑一周，看缓存命中率和首屏时间的变化，再决定要不要全站切过来。
